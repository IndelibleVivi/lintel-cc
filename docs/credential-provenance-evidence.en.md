# Credential provenance: evidence and implementation boundaries

November 13, 2026 · Engineering evidence record · [中文](credential-provenance-evidence.md). This document separates official mechanisms, Lintel's product decisions and missing device evidence. For user operations, see the [cleanup guide](cleanup.en.md). The additions belong to development source and are absent from the published App 0.1.1 and CLI 0.1.0.

## 1. How evidence was obtained

The review used current official Anthropic documentation and the repository's `cleanup.rs`, `auth_sources.rs`, `auth_cleanup.rs`, `keychain.rs`/`keychain/macos.rs`, `components.rs`, `startup.rs`, App cleanup flow and operation contracts. The retrieval date is November 13, 2026. Version numbers below are prerequisites stated by the documents, not versions executed during this review. This static mechanism review runs no real Claude process, login, logout, Keychain operation or model request. Ordinary development checks use synthetic roots and inert adapters; later independent temporary-Keychain platform API checks are recorded in [current state](current-state.md), without establishing personal-account acceptance.

Current documents may change and do not specify every historical client. Finite source recognition, observations from the current executor, explicit CLI status and real-client behavior remain separate evidence levels.

Earlier evidence statically inspected `cli.js` from official [`@anthropic-ai/claude-code` 2.1.101](https://registry.npmjs.org/@anthropic-ai/claude-code/2.1.101) without execution. The November 14 release audit also downloaded and statically inspected the embedded implementation in the official [`@anthropic-ai/claude-code-darwin-arm64` 2.1.325](https://registry.npmjs.org/@anthropic-ai/claude-code-darwin-arm64/2.1.325) Mach-O, checking the tarball against registry SHA512 integrity. The base service remains `Claude Code-credentials`; an explicit directory selector adds the first eight lowercase SHA256 hex digits of its NFC spelling. An unset default directory and the same explicitly set directory select different services. The newer `CLAUDE_SECURESTORAGE_CONFIG_DIR` takes precedence: empty selects the default/bare service, while a nonempty value determines secure-storage directory and service hash. These are versioned implementation observations, not a future compatibility contract or an authentication trial. The [authentication security audit](release-readiness-20261114/auth-security.md) records exact URLs, SHA256 values, byte anchors and fixes.

Lintel checks the bare service plus root hash for the default root, and hashes for custom roots. Matching inherited raw `CLAUDE_CONFIG_DIR` and `CLAUDE_SECURESTORAGE_CONFIG_DIR` spellings contribute their NFC hash only when they resolve to the selected root. Launch/status retains a matching absolute spelling and an unset ordinary default. Matching relative paths and cross-root or unverifiable secure-storage selectors are refused before execution. New launch/resume and cleanup plans requesting runtime status bind this choice; changed choices and unattempted older plans require a new preview, while attempted originals remain query-only. Version 2.1.325 also maps `USER` outside `[A-Za-z0-9._-]+` to another account, unlike the older implementation. Lintel reports unknown coverage for incompatible spellings rather than guessing or scanning other accounts; previously frozen item identities remain exact. Unknown historical aliases, other accounts and unknown container fields remain outside the supported scope.

## 3. What precedence establishes

The ordinary CLI order in [Authentication precedence](https://code.claude.com/docs/en/authentication#authentication-precedence) is: selected cloud provider, `ANTHROPIC_AUTH_TOKEN`, adopted `ANTHROPIC_API_KEY`, `apiKeyHelper`, `CLAUDE_CODE_OAUTH_TOKEN`, profile/federation, ordinary login. Interactive API-key adoption differs from noninteractive behavior, and gateway login has separate precedence. Profile authentication mode, explicit naming, existing login and host surface also affect selection.

Inventory therefore does not implement a simplified ranking that claims to identify the active source. It can report a variable's presence and empty/nonempty value state in Lintel, a helper declaration, or a credential container. `presence` records existence; `value_state` distinguishes empty, nonempty, unset and non-string values. Neither proves valid authentication. Only an explicitly requested official status command produces a client report for that executor, root and time. Even `oauth_token` does not prove a particular shell file supplied the token or that `setup-token` generated it; another OAuth access token can use the same variable.

Helper bodies, variable values, account identities and tokens never enter inventory, previews, ordinary records or logs. Unreadable or malformed sources remain unknown without revealing an excerpt for troubleshooting. Source IDs select structural locations within a host/environment; they are not transferable credential fingerprints.

## 4. Two product decisions

### Precisely edit identified sources

Source selection uses the existing `plan_cleanup`, approval, execution and receipt authority. A supported source needs an exact location, finite syntax, current file identity and content binding. Shared files change only within the frozen scope. Shell command substitution, control structures, functions, dynamic injection, unattributed Keychain objects and shared profiles remain unsupported for automatic removal; no content is executed to fill an evidence gap.

The cited official documents do not define a stable, complete private credential schema. This implementation recognizes `.credentials.json`'s `claudeAiOauth` slot and a string `primaryApiKey` in client state while preserving all other fields. That is finite implementation support, not a complete model of every version, API-key or MCP store. Unrecognized formats report a limitation. Default-root client state is `~/.claude.json`; a custom root uses its own `.claude.json`. Deleting either whole file would expand into unknown data and is not an implementation of selected-source cleanup.

Authentication cleanup creates no token-recovery backup. File replacements are computed in bounded memory; private persistent bindings contain salted digests, locators and identity metadata. The transaction moves the original into private staging beside the source, then publishes a replacement without overwriting another writer. That replacement can contain non-target credentials which must be preserved. Successful readback removes the original; interruption or conflict reports retained originals/staging in `retained_sensitive_material` and prevents a completion claim. If staging is renamed/replaced and identity is lost, `location_unknown` retains only the last known location, without scanning or treating the missing old path as proof of destruction. Public plans and receipts never include before/after content, and non-target secrets do not enter logs or an additional recovery package. Query the original task after interruption; replaying cleanup cannot establish certainty.

Production Keychain code uses Security.framework for finite service/current-account reads. Persistent references, accounts and per-plan salted whole-payload digests stay in private bindings. In-memory transformation removes only `/claudeAiOauth`, retaining `mcpOAuth`, `pluginSecrets` and unknown fields. `SecItemUpdate` changes data only while retaining the original item identity, without whole-item deletion, secret temporary exports or backups. Each item is limited to 1 MiB within the source module’s 8 MiB total. `limits.keychain_scan_complete` is distinct from file scanning, and `limits.keychain:"selected_services_only"` never attests the entire Keychain. Stopping known writers, immediate pre-update comparison and complete readback provide neither a true external-writer CAS nor cross-source atomicity. Changes or uncertainty retain the original task ID for inspection without automatic update retries.

### Refuse automatic official logout with broader effects

The user explicitly required preservation of MCP and other work. The documented extra effects of `/logout` conflict with that scope. CLI `auth logout` has no verified adapter meeting the preservation requirements, and this development performed no real-client trial of either entry. A new request for automatic logout returns `official_logout_scope_unsafe`. An old unexecuted plan without the new safety binding, or one requiring logout, returns `stale_auth_plan` and requires a fresh preview. Accepted original jobs remain queryable. The old optional logout path must not be described as a newly verified safe mechanism, and a generic checkbox does not resolve its collateral effects.

The official-logout limitation does not forbid exact Keychain cleanup. Recognized fields use the plan path above; unselected services, other accounts, locked stores and unknown formats retain separate uncovered/unresolved states. Users choosing official account management still need to review MCP/plugin reauthorization effects. Lintel does not initiate it or interpret local removal as server revocation.

## 5. Four independent verification conclusions

1. **Selected local sources:** whether the frozen assignment/JSON field remains at its original location. New writes, unreadable sources and unfinished edits retain their own status.
2. **Current executor:** whether this App/runner still inherits relevant variables and whether optional official status reports authentication. Lintel cannot rewrite a parent shell or other existing processes.
3. **Other contexts:** Terminal, IDEs, custom launchers, services, other hosts, CI and administrator injection require separate checks. Absence from this observation is not universal absence.
4. **Server revocation:** without independent server evidence, this remains unverified. A missing local declaration does not prove token invalidity.

Completed selected local steps and remaining authentication can both be true. Independent `auth_verify` rereads sources instead of copying the cleanup receipt. Only explicit `observe_runtime` runs the official command, before the final local reread so status/helper credential regeneration can be observed; that command is not a purely static observation. Verification errors and uncovered sources must never become a green success claim.

## 6. Versions and further evidence

Static JavaScript evidence from 2.1.101 and native darwin-arm64 evidence from 2.1.325 support the bounded recognition and directory-selection fixes above. Neither real client was executed, logged in/out or used to alter a real Keychain in this review. Earlier metadata-only coverage of 2.1.323 remains historical evidence and does not remove the need to recheck later versions. No official logout parameter meeting the preservation scope has been established. Native API and real-client acceptance remain separate: the former uses `keychain-native-test` in a temporary Keychain under a disposable GitHub-hosted macOS account, never an implicit personal-machine run. The latter still needs independent default/explicit-default/custom-root, secure-storage selector, accessible/locked-Keychain, file-fallback coexistence, launch-context and MCP/plugin preservation evidence. Ordinary `cfg(test)`, temporary-HOME and `LINTEL_TEST_HOME` checks use an injected `.lintel-test-keychain.json` inside a temporary home. Fresh-process CLI regressions additionally use inert clients, real PTYs and production Linux `/proc` writer inspection; these do not attest real authentication. See [current-state.md](current-state.md) for native acceptance status, with source, synthetic behavior, native API and actual user login recorded separately.

This record does not certify an App/CLI release, website deployment or real-user cleanup. [current-state.md](current-state.md) tracks exact engineering checks, commits and release status.
