# 调查笔记：哪些证据真正改变了产品设计

**核验日期：2026-10-02。** 本文件是证据摘要与设计判断，不是竞品测评报告或已完成的实机验证。主要资料来自官方产品文档、浏览器/平台文档与项目上游。网页将继续变化；实现时应保存实际验证版本和只包含必要材料的证据记录。

## 1. 最重要的结论

本工具值得成为 App，但前提不是“把几个命令做成按钮”。值得安装的部分是：准确定位使用环境、直接应用方案、真实操作浏览器、处理登录与工作数据的混合存储、跨机器保持同一执行语义、升级后检查漂移，以及在清理后完成重建。

相反，如果成品只有风险标签、隐私建议、设置跳转和一个大的“已保护”，独立产品的理由不足。这是产品判断，不是从某条技术文档直接推出的事实。

## 2. 证据与设计的对应关系

### R01 · 一个 API 域名可能同时承载业务与额外流量

**来源事实。** 当前官方网络表将正常 API 请求、部分 feature flags 和 telemetry event logging 列在同一个 API host 下。[S02]

**影响。** 不能复制历史的“屏蔽几个域名”清单，便声称精确阻止所有遥测。不解密 TLS 的 CONNECT proxy 看不到内部每条请求的用途。

**采用。** 官方产品开关处理产品自己可区分的功能；浏览器原生规则处理其可区分的请求；出站通道处理目标范围和路径；观察记录只陈述实际能看见的部分。

**仍需验证。** 当前发行版在各认证方式下的实际行为，更新后域名/用途变化，以及禁用开关对业务能力的影响。

### R02 · “关闭非必要流量”不是所有额外请求的总开关

**来源事实。** 官方说明总开关有另行控制的例外；关闭部分指标控制也会停止 feature-flag evaluation，可能影响 Remote Control。[S01]

**影响。** UI 需要列出独立的控制面和功能依赖，不能显示一个“全部已关闭”。预设必须按用户是否保留某项功能形成有意义的选择。

**采用。** 默认采用独立设置；总开关是有完整影响说明的可选项，不是用名字推断出来的万能方案。

### R03 · 配置根、凭据根、启动上下文不能合并成一个路径

**来源事实。** 当前官方说明 macOS 使用 Keychain，也存在写入失败时的文件 fallback；配置目录可以影响凭据归属，但另有 Console 认证存储例外。[S03]

**影响。** 清理一个目录不一定清掉目标登录；设置两个目录也不自动证明两种认证完全独立。

**采用。** Environment 分别记录 config root 与 credential scope。logout、remove-local、state-reset 是不同动作；共享身份先展示受影响的对象。

**仍需验证。** 所支持版本的真实 credential namespace，旧安装升级后的遗留物，Keychain 锁定的 SSH 情况。不要从本次文档推断所有历史版本都如此。

### R04 · 更新配置文件与更新 shell 环境有不同的生效语义

**来源事实。** 当前 env 文档区分 settings.env 应用与 shell 启动继承；移除变量与新增变量也不是相同的运行时行为。键的优先级不能用一条通用规则概括。[S04][S05]

**影响。** 一个“写入成功”的按钮不证明现有进程采用了新值。刷新配置也不能一律要求重启整个环境。

**采用。** 每个动作记录生效时机、来源链、运行上下文证据。为新启动提供用户可直接使用的入口；已有会话的改变有明确说明。

### R05 · 官方命令能够减少对私有状态的依赖，但命令也要适配

**来源事实。** CLI 文档列出非交互认证状态、注销和安装/设置诊断入口；状态输出字段有版本条件。[S06]

**影响。** 可以把真正能做的动作带进 App，不必只给设置链接。但运行一个命令不天然等于“完全离线、无副作用、输出永不变化”。

**采用。** 对命令、版本、调用环境、权限和输出 schema 建立测试；无支持时不启动交互 agent 当扫描器。

### R06 · 浏览器能够提供实际清理和隐私控制

**来源事实。** Chrome 提供 browsingData、contentSettings、privacy、proxy 和声明式网络规则等原生 API。[S07][S08][S09][S15][S16]

**影响。** 只做“点这里打开设置”没有充分利用可实现能力。浏览器伴随扩展应该是正式组成部分。

**采用。** 扩展在自己的 profile 内执行动作；应用负责跨表面任务与结果。业务执行不要求主应用读取 Cookie 值或截获用户聊天。

### R07 · 站点级删除有真实范围差异

**来源事实。** Chrome 的 Cookie origins 清理涉及完整可注册域；Firefox 提供不同的 host/store 范围机制，且 removeCache 的参数不能使它成为站点级清理。[S07][S11][S12]

**影响。** “清一个站点”可能退出同域其他子站登录，“Firefox 清某站缓存”可能实际清整个 cache。

**采用。** 预览展示真实范围。HTTP cache 与站点存储分开，不能定向时默认不扩大操作。用合成邻域数据验证保留，而不是只检查目标消失。

### R08 · 改 WebRTC 策略与关浏览器定位不是一件事

**来源事实。** Chrome/Mozilla 有 WebRTC 网络隐私设置；Chrome 的站点功能权限由另一个 API 管理。[S08][S09][S30]

**影响。** 按 profile 生效的媒体路由设置不能被标成每站点设置，也不能被标成全设备无泄漏。可控项还可能被其他扩展或策略控制。

**采用。** 在界面呈现作用范围、level of control 和媒体功能影响，并检查真正有效值。[S13]

### R09 · 独立 browser data root 是可行的便利机制

**来源事实。** Chromium 文档公开 user-data-dir 的位置与覆盖方式。[S14]

**影响。** 没必要为了专用使用环境打包一份浏览器。也不能认为命令行参数出现，就证明启动进入了正确 profile。

**采用。** 使用用户已有浏览器，创建专用入口，并用配对信息和实例观测确认目标。进程复用与同步设置是测试重点。

### R10 · Native Messaging 不是一个足够完整的授权系统

**来源事实。** Chrome 的 native host 有扩展 allowlist，通过浏览器发起进程与消息；文档也要求校验网页转来的消息。[S10]

**影响。** 扩展 ID 不区分其在不同 profile 中的安装，允许扩展通信也不意味着允许网页删除系统文件。

**采用。** 增加实例配对、目标 capability 与计划授权；Native Messaging host 不开放任意 shell 或路径读写。

### R11 · 浏览器扩展的安装体验必须算进产品

**来源事实。** Firefox release/beta 的扩展需经 Mozilla 签名，自分发也一样。[S24]

**影响。** 给用户一份源代码，让其永远临时加载，不是完整安装体验。首次浏览器授权不可悄悄绕开。

**采用。** 整版交付包含可持续安装的扩展产物、升级和配对恢复；用真正的 release 浏览器验收，而非只测试自动化专用构建。

### R12 · 有系统网络约束能力，但需要真实覆盖测试

**来源事实。** Apple Network Extension entitlement 允许特定网络过滤能力；上游 LuLu 说明其规则及主机名识别存在平台覆盖限制。[S17][S19]

**影响。** “安装了网络扩展”不等于能精确区分某个 Chrome profile；“解析到一个 IP”不等于能识别共享 CDN 上的具体用途。

**采用。** 强约束与普通受控通道分开。Mac 先证明进程身份和范围，再承诺；不能偷偷扩大到整个 Terminal 或所有浏览器。

### R13 · Linux 网络 namespace 是实现入口，不是配置文本魔法

**来源事实。** systemd 支持网络 namespace 相关机制；其源代码也区分不同能力缺失的路径，某些配置可能在缺乏支持时继续运行。[S21]

**影响。** 写出配置文件不证明强约束实际存在。

**采用。** runtime capability 检查、直接出站负例、IPv6/UDP/子进程覆盖都加入验收；不改变宿主机默认路由。此处是设计路线，还没有本任务的 Linux 实机证明。

### R14 · SSH 能省掉公网管理服务，但不能省掉任务语义

**来源事实。** OpenSSH 支持远程命令、连接验证等能力。[S20]

**影响。** SSH 是 transport，不替工具保证业务幂等或断线后进程存活。

**采用。** 每台主机有自己的 durable job journal；提交结果与连接状态分离；ACK 丢失查询原任务，而非自动再删一次。

### R15 · Desktop 不能直接继承 CLI 的承诺

**来源事实。** 官方存在 Desktop enterprise 配置，以及专门针对 Desktop on third-party inference 的 telemetry 文档；它们有明确适用范围。[S27][S28]

**影响。** 不能把 3P 文档中的配置无条件套给所有消费版 Desktop，也不能把 Mac 上的动作延伸成云端 Cowork 控制。

**采用。** 独立的 Desktop adapter；未知布局先静态检查与归档，不臆造“官方 profile 隔离”。

### R16 · 降低本机外发与撤回服务端信息是两件事

**来源事实。** Anthropic 隐私政策列出设备/连接信息、标识符与使用信息等类别，但没有提供可直接拿来实现“封号风险评分”的判定算法。[S29]

**影响。** 数据清除必须明确自己在哪一侧发生。公开政策本身不足以证明某个环境字段造成封禁。

**采用。** 本地清理、远端令牌撤销、账号状态三个字段分开。没有“已洗白”或“防封成功”的结果状态。

## 3. 同类机制比较，而非虚构竞品缺陷

| 参考 | 实际可借鉴的东西 | 不应直接继承 |
|---|---|---|
| CC Switch 上游 [S18] | 用户意图驱动的配置管理、桌面操作入口、保留已有配置 | 不把本项目扩成多模型额度/路由管理器，不读赞助文案来证明供应商质量 |
| LuLu 上游 [S19] | 应用/连接规则、profile、可见的允许/拒绝与临时动作 | 不把通用防火墙替代产品级语义，不假定域名在所有流量都可识别 |
| 浏览器原生扩展 API [S07–S16] | 真正执行删除、权限设置和连接策略 | 不假设不同浏览器的参数完全等价，不把 API callback 当全部残留验证 |
| 用户两张截图 | 组合操作的便利、清理与保护放在同一个产品 | 卡密、官方风格借用、重复结果、模糊“防封”、来源不明的效果宣称 |

此次未运行这些参考产品来比较速度、内存或真实成功率；不能写“我们的更快、更安全”作为现成事实。Spec 规定的是新产品应实现的差异。

## 4. 用 Soundings 修正了什么

原方案把“环境”误解成开发者缓存与磁盘维护，从而将最重要的浏览器/遥测/封号后清理降级。纠正应传播到首页、功能默认、对象模型、测试和验收，而不是只换标题。[S31]

对完整目标进行外部调查，是为了发现机制和推翻假设，不是为了凑参考数量或把工作停在报告上。[S32] 因此本次交付以可直接实施的完整 Spec、具体旅程和失败拒绝验收收尾，而不是另发一个缩小范围的提纲。

## 5. 尚未取得的证据

- 第三方 ZIP/`.app`：本对话无附件，只有截图。
- 作者的 Mac/VPS 当前真实配置：没有读取或修改；不能把私有服务名称、状态当作本次检测结果。
- 实际产品/扩展安装与运行：本任务在文档层完成，未实机验证目标应用。
- Mac 网络扩展签名资格与进程隔离覆盖：需要实施期探针。
- Desktop 私有数据布局与历史版本：需要自己的安装/配置矩阵，不从第三方清理器照抄路径表。
- 账号封禁的具体判定：公开文档不足以支持风险预测，不应制造证据。

## 6. 实施期优先取证清单

先完成四个有区分力的实验：两个 profile 的配对/清理是否真的隔离；两种认证作用域是否真的独立；同一个控制值在终端/IDE/service 中何时生效；宣称强约束的通道是否能阻挡直接 IPv4/IPv6/UDP 和子进程请求。

每个实验都保留：版本、输入、操作、观测方式、对照、未覆盖项、如何复现。失败时修正受影响的设计，不把全项目降级为只读扫描器。
