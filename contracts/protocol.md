# Lintel JSON protocol 1

All requests: JSON object with `command`. All responses: `{ "ok": true, "data": ... }` or `{ "ok": false, "error": { "code": "...", "message": "..." } }`. Rust shared public entry: `lintel_core::handle_request(request: serde_json::Value) -> serde_json::Value`. State uses LINTEL_STATE_DIR override, otherwise an OS user app-data directory. Synthetic tests use LINTEL_TEST_HOME only in CLI/development, never embed user fixtures.

Commands and data:
- `discover` → `{environments: Environment[], capabilities: {name, status, reason}[]}`. May register discovered default root in owned inventory; never execute target software during scan.
- `register` + `name`, `root` → Environment. `create_environment` + `name` → Environment with fresh owned root.
- `inspect` + `environment_id`, optional `trusted_devices` (same user-declared enum) → `{environment, settings: Setting[], assets: {category,count,bytes}[], warnings: string[], policy: PolicyAssessment}`. Never return secrets or whole JSON settings.
- `plan_policy` + `environment_id`, `preset` (`preserve`|`reduce`|`custom`), `keep_remote_control` boolean, optional `trusted_devices` (`unknown`|`required`|`not_required`), optional `release_settings` (selected conflicting keys: DISABLE_TELEMETRY, DO_NOT_TRACK, DISABLE_GROWTHBOOK, CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC) → Plan. Selection only authorizes preparing explicit deletion differences; execute still requires the exact approval hash. Unknown values/keys are rejected. Custom uses optional `custom_settings: {known_env_key: "keep"|"disable"|"remove"}`; absent keys keep their original values. Only the seven modeled variables are accepted. `disable` writes string "1" only if the existing value is not already disabled under that variable's semantics; `remove` deletes this root's env field, not other sources. Non-custom presets reject any custom map; custom rejects nonempty `release_settings`. All-keep/no-change custom plans preserve original settings bytes, permissions and file absence. See [the core contract](../docs/core.md).
- `plan_reset` + `environment_id`, `recipe` (`rebuild`), `categories` (selected work classes) → Plan. Legacy rebuild keeps its established semantics: it homes the work archive and a fresh root, leaves the original root/login intact, and its receipt stays `partially_completed` (old cleanup never claimed). Other cleanup recipes use plan_cleanup; complete credential/writer coverage remains unverified.
- `plan_archive` + `environment_id`, `categories`, optional absolute `output_path` → Plan (`kind:"archive"`, `outcome:"archive_only"`) that only encrypts the selected work. It never creates a root, never touches settings/credentials, and leaves the original files untouched. If `output_path` is given the resolved absolute path is frozen at preview, must not already exist, and is never overwritten; without it the archive stays in the private state so the receipt can point back to it. Execute requires the archive passphrase.
- `plan_preserve` + `environment_id`, `categories`, optional `name` → Plan (`kind:"preserve"`, `outcome:"preserve"`) that encrypts the selected work, creates a fresh owned root and migrates the selected categories. The receipt completes with `outcome:"preserved"` and a `coverage` block (`old_login`/`old_root` retained, `service_binding:"unchanged"`) and `next_steps`; the retained old environment is reported as a `preserved` step, not an outstanding task.
- `plan_show` + `plan_id` → the deeply frozen Plan as a preview would render it (private raw snapshot, root identity and `extra` stripped). No passphrase or secret is ever stored in a plan, so none can be returned. Missing/damaged plan is a specific error.
- `cleanup_inspect` + `environment_id` → `{files,writers,services,shared_profile_present,official_logout_available,coverage}`. Metadata only. `services` is an array of live-verified owned holds (`manager`, `unit`, `quiesced`, `quiesce_job_id`), or `{code,message}` when service inspection fails. The latter does not authorize cleanup; plan creation and execution must recheck service state successfully.
- `service_inspect` + `environment_id`, `manager` (`user`|`system`), exact `unit` (`.service`) → binding, effective unit/restart/process/cgroup facts, owned persistent hold and original quiesce job. Linux only; system manager requires the current runner to be root, with no automatic sudo.
- `plan_service_quiesce` + the same fields → Plan with frozen unit sources, original state and one persistent owned start blocker. `plan_service_resume` + original `job_id` → independently approved Plan; changed sources or hold ownership block restoration. Both execute through the existing exact approval/journal path. See [service scope](../docs/services.md).
- `auth_probe` + `environment_id` → sanitized `{auth_method,logged_in,...}`. Explicitly runs the target CLI auth status; requires matching configDirectory.
- `plan_cleanup` + `environment_id`, `recipe` (`repair_login`|`reset_client`|`retire`), `writers_confirmed_stopped:true`, `official_logout:boolean`, `categories` → Plan. Scope/executable/files are checked again at execution; reset/retire require an archive passphrase. Canonical reset order is frozen in `actions` and reproduced in the ordered receipt `steps`: quiescence recheck → state backup + encrypted work archive → (reset_client) fresh root + migration → official logout (if selected) → exact local file removal → (retire) retirement. No destructive step precedes preservation; reset_client rechecks its just-written archive against the receipt digest before creating/migrating into a new root, rejecting replacement as stale_archive; a failed logout retains the archives, the prepared new root and its completed steps, and performs no local removal.
- `reactivate_environment` + `environment_id` → Environment. Re-enables registration without restoring credentials.
- `archive_inspect` / `archive_read` / `plan_import` accept exactly one archive source: `job_id` (this install's own job, whose recorded `archive_path` and available `archive_digest` are rechecked; replacement yields `stale_archive`, while legacy receipts without a digest retain compatibility) or an explicit absolute `archive_path` so the package can be carried to another Lintel install with no access to the original job/inventory. Supplying both or neither is rejected. Strict named/finite requests require at least one selected category (`minItems:1`); raw protocol-1 defaults remain compatible. The package is self-contained (`schema`, `generator`, `created_at`, per-file `path`/`category`/`digest`); `generator` is declared package metadata, not authenticated provenance: newly written packages declare `"Lintel"`, while inspect returns the package string or `null` for legacy/unknown metadata; external packages are judged on their own contents and the read/limit/path/category/digest guards are identical. `archive_inspect` → `{job_id,archive_path,created_at,generator,schema,categories,files:[{path,category,bytes,digest}],notes}`. `archive_read` + `path` → `{path,text,bytes,truncated}`, maximum 1 MiB text preview. `plan_import` + `environment_id`, `categories` (+ the chosen source and passphrase) → Plan that freezes the source and the encrypted archive digest; execute re-reads the same source, rejects a changed `stale_archive`, and never overwrites an existing or unselected target. Wrong passphrase/corrupt/escaping/duplicate/unsupported-category packages are refused.
- `plan_restore` + `job_id` → Plan with field-level conflict checks.
- `execute` + `plan_id`, `approval` (=plan.hash), optional `archive_passphrase` → Receipt. Any plan with archive_passphrase_required requires a passphrase of at least 12 characters; never persist or log it. Persist plan/journal before side effect; repeated ID returns original receipt, never repeats.
- `jobs` → `{jobs: Receipt[]}`; `job` + `job_id` → Receipt.
- `drift` + `environment_id` → `{changes: Setting[], status}`; `accept_drift` + environment_id records current owned settings as baseline.
- `launch_context` + environment_id → `{root,executable}` for the interactive CLI and remote launch preflight; rejects retired environments and missing executable.
- `launch` + environment_id, optional `proxy_url` (loopback HTTP address only) → `{status,message}` using exact executable/root; never shell-interpolate user text. UI action is explicit launch approval.
- `export_support` → structured redacted data, no auto upload.

Environment: `{id,name,host,surface,root,executable: string|null,ownership,status}` plus additive `product_version` and `product_evidence` from static installation metadata (never run Claude).
Setting: `{key,label,value: string|null,source,effect_timing,status}` plus additive fields; seven modeled settings rows, each with its distinct value semantics and `runtime_verified:false`.
Plan: `{id,hash,environment_id,title,kind,changes: {key,label,before: string|null,after: string|null,path}[],preserves: string[],warnings: string[],actions: {id,label,reversible}[],created_at,status}`. Additional fields include `archive_passphrase_required` and `file_count` for rebuild/archive/preserve, plus `outcome` and (for archive) `output_path`; immutable target snapshot held privately. Policy plans also freeze the detected executable/version evidence; changes before execute return stale_product. An older policy rule requires a fresh preview.
Receipt: `{id,plan_id,environment_id,title,status,steps: {id,label,status,message}[],created_at,restorable:boolean,warnings:string[]}`. Store per-step status and uncertain effects. No unverified success. A failure after durable accept persists a structured `error: {code,message,phase,step_id,uncertain_side_effects,recovery}` where `phase` is the real receipt status at failure (`executing` or `verifying`) and `recovery` always directs the caller to query the original job by the same ID; completed steps and produced artifacts (archives, new root) are retained and no destructive step is replayed. New-root creation and migration persist an active `create`/`migrate` step before mutation; a failed migration retains the new root and published files and reports the active step with `uncertain_side_effects:true`. Work receipts additionally carry `archive_path`/`archive_digest`, and archive/preserve receipts carry `coverage` and `next_steps`. Policy plans and receipts include the same frozen `policy` assessment: `{rule_version,product,rules,remote_control,current_remote_control,release_settings,supported_presets,preset,custom_settings?}`. Remote Control is configuration evidence only, with `runtime_verified:false`; organization conditions are user-declared.

Desktop Tauri command `request` accepts `{payload: request}` and returns the envelope. Frontend adapter throws useful errors. Browser preview may use a visibly marked isolated synthetic transport; production uses Tauri only. No silent fake-data fallback.

Service plans/receipts add `service: {manager,unit,root,before:{active_state,sub_state,unit_file_state,restart},after:{active_state,hold},hold:{path,persistent:true},original_job}`. Receipts additionally record actual `service.observed` and `service_restorable`; a post-reload configuration mismatch adds finite `service.configuration_conflict` difference keys, safe property values and file identities, without environment values or source paths (see [the service guide](../docs/services.md)). Service restoration uses `plan_service_resume`, independently of settings-field `restorable`. A stored completed quiesce receipt alone does not prove that the service remains stopped now; inspection and cleanup recheck the manager and cgroup.

Browser native and network modules use explicit Tauri `browser_request` and `network_request` commands, documented in docs/browser.md and docs/network.md. They cannot invent generic system exec/read/delete endpoints.

## Integration decisions

- CLI binary is `lintel`; `lintel request` reads one JSON request from stdin, prints one envelope. No startup chatter on stdout.
- `job` accepts `job_id`; lookup should also accept `plan_id` when execute response was lost. Stable ID must be computable before submission (prefer receipt.id = plan.id).
- Reset/migration work selection uses category identifiers `instructions`, `memory`, `sessions`. Unsupported categories must return explicit validation error, not silently drop.
- Desktop Tauri is a standalone Cargo workspace with path dependency to crates/core; root default members core+runner+egress.
- Browser native host remains standalone under extensions/browser/native-host, with a path dependency from the desktop and a finite browser_request control adapter. Desktop bundled_host_plan selects only browser and exact extension ID; install_bundled_host approves the complete frozen plan and rechecks it before installing the bundled executable into current-user stable storage and registering it. Desktop rejects the manual host-path installer operations; those remain available through the independent CLI. Profile pairing remains separate. See docs/browser.md for fields and upgrade boundaries.
- Desktop bundled_extension_plan previews actual App extension files for a named browser; install_bundled_extension approves the complete frozen plan to prepare a stable current-user directory, with ownership-checked update and explicitly approved interrupted recovery. reveal_bundled_extension accepts only a named browser and opens its managed fixed directory in Finder. These operations do not write browser profiles/preferences, load an extension, register the host or pair a profile. See docs/browser.md for fields and loading instructions.
- Remote queries use `request`; execute uses `submit`, through the bound App runner path or legacy PATH `lintel`. Only a validated runner digest can select the bound path; ordinary request fields stay in JSON stdin, never user-interpolated shell commands. Interactive remote launch is a separate finite operation: validates alias/id, preflights launch_context, then requests macOS Terminal to run fixed strict SSH + PTY + bound runner launch id; no remote-returned path enters the local shell. submit returns a durable accepted Receipt before its detached worker finishes; query the original job for completion. `discover` through runner request adds the detached_submission capability. Desktop `remote_request` has finite alias/host/connect/request/execute/reconnect and prepare_runner/install_runner/query_install/launch operations documented in docs/remote.md.

`Inspection.policy`, `Plan.policy`, `Receipt.policy`: `{rule_version, product:{version,source,executable}, rules:[{key,label,value,disabled:boolean|null,semantics,scope,effect_timing}], remote_control:{status,summary,blockers,trusted_devices,trusted_devices_source,version_family,runtime_verified:false,unverified}}`. All new assessments include `supported_presets:["preserve","reduce","custom"]`. Plan/Receipt include frozen `preset`, `keep_remote_control`, `release_settings`, `current_remote_control`, and `custom_settings` for custom policies. A GUI connected to an older runner must not infer custom support from the presence of seven rules; it requires the advertised preset. Rule v3 requires a new preview for old pending policy plans, while completed receipts and restoration remain available. The three Remote Control statuses are `blocked`, `conditional`, `configuration_compatible`; none establishes account or live runtime availability. User settings values alone do not establish effective shell/project/managed state.

迁入整批工作时，共同路径分配保留已有 `lintel-imports` 逻辑位置；活跃 `projects` 与待用区同名或出现文件／目录冲突时，为冲突的文件项选择未被本批原名称、父目录或已分配名称占用的 `lintel-N-` 文件名前缀，保留文件后缀与类别。preserve/reset_client 与独立 plan_import 共用此分配；import 预览冻结实际 destination，执行在任何写入前复核整批目标，旧的歧义目标计划返回 stale_plan 并要求重新预览。已有目标内容仍返回 import_conflict，不被覆盖。

archive 发布前持久记录执行中的步骤、archive_path 和 archive_intent_digest（准确待发布密文）；完成和 archive_digest 仅在写后读回成功时记录。中断后 job-scoped inspect/read/import 使用完成 digest，缺少完成 digest 时使用 intent digest，从而可读取真实已发布包而不误归属后来替换的包；两个 digest 均无的旧回执保留兼容。路径记录不宣称完成或文件必然存在，未发布文件返回具体读错误。
