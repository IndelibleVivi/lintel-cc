Lintel App updates and release preparation

简体中文 (canonical) · English · Documentation

This guide covers manual installation, the macOS App updater and release preparation. The v0.1.1 developer Preview repairs the bundle-signing defect in the 0.1.0 DMG. All four public assets—the DMG, paired installation notes and checksum list—were checked, and the Chrome-downloaded DMG was mounted read-only with its contained App passing strict signature verification. The old 0.1.0 DMG remains for history and should not be installed. The App has a complete ad-hoc signature but no Developer ID or Apple notarization, and no release public key or activated feed. Gatekeeper may still reject the unnotarized download. Open Anyway was observed in this trial; a per-App trust exception is not clean-Mac acceptance. See current state (Chinese) for exact evidence. The CLI retains its separate Agent CLI procedure and original candidate version.

Manually installing the developer Preview

  1. Download the matching DMG from the website or current GitHub Preview Release, and read that Release's installation notes. The App currently supports Apple Silicon only. Compare shasum -a 256 for the DMG with SHA256SUMS from the same Release. A checksum establishes matching bytes, not Apple authentication or installability.
  2. Quit other Lintel copies, open the DMG and drag Lintel.app into Applications. Keep the previous App before replacing it. User materials and task records live separately from the App bundle; do not delete them to retry startup.
  3. First launch may show an unidentified-developer or notarization warning. Only after checking the source and deciding to trust this Preview, follow Apple's per-App exception instructions: look for Open Anyway in System Settings → Privacy & Security, then confirm it yourself. This does not disable global Gatekeeper. Some systems or management policies may not offer the option.
  4. If the App is still reported as damaged, cancel first. Do not repeatedly reinstall or change global security settings. Check the version and download checksum, then run the read-only checks below and retain the full error for a report. A valid strict signature still does not establish Developer ID, notarization or Gatekeeper acceptance.
   codesign --verify --deep --strict --verbose=4 /Applications/Lintel.app
   codesign -dvvv /Applications/Lintel.app

Removing one App's download quarantine is a separate, explicit trust exception. The build, installer and App never do it automatically. This project does not provide instructions to disable global Gatekeeper.

Using the App

Open Settings and modules → Lintel version and updates. The version comes from native App package metadata. The build fixes the channel; Webview requests cannot select arbitrary URLs, public keys, downgrades or installer arguments.

  1. Check for updates. A manual check accesses the fixed https://lintel.page/updates/preview.json or stable.json. An unconfigured build explicitly reports unavailable. Offline operation, absent feeds and invalid responses are errors, never “up to date.” A successful check establishes only that the channel has no higher version or has a candidate.
  2. Download and verify. The official Tauri updater verifies downloaded bytes and signatures, then checks the version in the signature's trusted comment. A download-complete event is not verification success. The candidate freezes its version, signature, URL and this attempt's ID; checking again invalidates the old candidate.
  3. Review and install. App replacement requires selecting and approving the current candidate. Native code excludes this App's running core, browser, SSH and network operations, and refuses installation while a controlled proxy remains active. Checking and downloading can proceed independently. The original intent is persisted before installation; unconfirmed intent publication prevents installation.
  4. Save your work, then restart. Installation does not restart automatically. An explicit restart is accepted only after checking native activity and proxies again; save any handoff draft first. The updater does not kill external Claude sessions or detached remote tasks; query original tasks by their original IDs.

Background checks default off. When explicitly enabled, they run only while the App is open and visible, at most once an hour. Closing Settings does not stop a selected check; deselecting stops it immediately. They never automatically download, install or restart, and are not a menu-bar/system background service. Preferences reside only in the current user's App data; they do not initialize Claude/core state.

Requests expose the egress IP and ordinary HTTP information to the Lintel feed/GitHub host. They upload no Claude roots, accounts, sessions, environment inventory or device identifiers. They are managed separately from Claude Code telemetry settings. Package admission is 512 MiB, with a five-minute total download deadline and a 25-second total check deadline. The official updater parses check responses; notes/signature and candidate origin are bounded after a successful response. This is not a generic feed or arbitrary HTTP client.

Uncertain results and version boundaries

Update records retain the original ID, starting/target versions and attempt result. On reopening, incomplete installation intents show interrupted; failures or unconfirmed record publication show uncertain, with no automatic replay. A further installation is refused while the old version is still running with an unconfirmed installation. Check the App location and version, and if needed repair manually using the official DMG. Observing the target or a higher running version can unblock future upgrades, but never rewrites the original interrupted record as completed.

When multiple App copies under one user share records, locking and readback comparison prevent an old copy from overwriting a newer intent. Activity/proxy checks cover only the current App process; they do not prove that other App copies, CLIs or external programs have stopped. Close other Lintel copies before installation. Damaged or externally edited records cause explicit refusal and remain available for inspection.

Cancelling an operation wait does not release a still-running blocking core check early. If a channel-stop wait is cancelled, the unfinished original channel continues to block installation; a later explicit stop continues to reconcile the same task.

SemVer comparisons use precedence only: 0.1.0-preview.1 is lower than 0.1.0; +build does not increase precedence; an equal version is not an upgrade. A next preview can use 0.2.0-preview.1, higher than the current version. Preview and stable feeds are separate; stable accepts no prereleases. Preview selection does not use GitHub releases/latest. Older installed Apps without the updater/public key need one manual upgrade.

Local Preview DMG and third-party notices

A DMG can still be built locally without Developer ID for inspection. A Preview must have a complete bundle-level ad-hoc signature: Info.plist must be included and Contents/Resources sealed. This is distinct from Developer ID and does not establish notarization or Gatekeeper first-install acceptance. A build alone neither publishes downloads nor activates the updater. Do not use --no-sign; the shared entry signs the fully assembled App before generating the DMG.

Prepare both Linux runners first if bundling their installation capability, then use clean source and the controlled entry below. It reuses the caller's Tauri/Cargo target cache and toolchain environment. Only when the config has no nonempty signingIdentity and neither APPLE_SIGNING_IDENTITY nor APPLE_CERTIFICATE is present does it add an ad-hoc fallback for this local build:

cd apps/desktop
npm run desktop:build:macos-preview -- \
  --out "/path/to/new/lintel-preview-$(date +%Y%m%d-%H%M%S)"

The entry requires a new candidate directory and never overwrites existing content. One tauri build --bundles app,dmg signs the assembled App and generates the DMG, then scripts/verify-macos-bundle.mjs rejects linker-only output, an unsigned Info.plist, an absent resource seal and strict-verification failures. It reads Info.plist entries and Sealed Resources version/files from codesign -dvvv; it never turns success by filtering codesign --verify output. Changing a signed resource or the plist fails. The copied App passes the gate again; the DMG is copied only, with no claim of DMG signing, read-only mounting or verification of its contained App.

To check an already controlled bundle:

node scripts/verify-macos-bundle.mjs /path/to/Lintel.app

Preserve each candidate with its source revision, architecture and actual checks, retaining previous packages. This neither replaces Applications nor bypasses Gatekeeper. Apple Developer ID, notarization, real first installation, GitHub Release, website downloads and feed activation remain separate steps. macos-bundle-signature-test uses a synthetic App to prove that the old linker-only state fails, a complete bundle-level ad-hoc signature passes, and resource/plist tamper is rejected. It neither runs the native App nor replaces a real candidate build.

build:desktop-resources automatically runs scripts/prepare-rust-notices.mjs to collect target-relevant normal/build dependencies from three locked Cargo manifests offline, plus current Rust standard-library notices. It requires rust-docs and cached dependencies; missing text or exact upstream evidence refuses preparation. The collection includes build/proc-macro dependencies and is not an exact linked SBOM. contracts/third-party-notices retains version-bound supplements and sources. Reused runners require their original toolchain notices; current toolchain text is not proof of how an older binary was built.

Vite's built-in build.license generates frontend licence and copyright texts. The full build runs Vite before the notice generator validates and collects its output; missing or empty text refuses preparation. Native tests may use the resource directory containing only its tracked README, which is not a distribution. Both sets ship under Contents/Resources/third-party-notices; retain subdirectories and HTML relative links. Generated output stays out of Git. Third-party terms do not select a licence for Lintel original code, documentation or independent assets. Rights for third-party identity/assets such as Clawd still require separate confirmation.

Standalone CLI distribution archives also retain third-party notices. package-cli.mjs --notices reuses the complete directory above, freezes its finite notice/license files and includes them in each archive’s metadata and checksums. First verify that the notices match the actual executables’ build toolchains; current texts cannot attest an unknown older build. Existing synthetic packaging callers that omit notices remain for local testing only.

Candidate first-use acceptance

Use a Mac matching the candidate architecture and record the exact DMG, source revision, App version and macOS version. The following is a repeatable native procedure; see current state for the latest candidate results. Existing CLI or Chromium checks do not replace native acceptance.

  1. Identify the tested package. Mount the local candidate read-only and copy the App into a new test directory, preserving the DMG and existing installations. Test actual download/Gatekeeper behavior separately on a clean Mac. Record the original system message and stop if blocked; do not remove quarantine or disable security checks. Website download acceptance first requires authorization to publish downloads, then verifies that the downloaded bytes match this accepted candidate.
  2. Prepare six synthetic originals. In a separate child shell, follow quickstart step 1, creating only the fixture without continuing to CLI registration or submission. Retain the printed ROOT; never point at a real Claude root. Replace APP below with the absolute path of the copied candidate and launch through macOS LaunchServices in the background from the same child shell. Fully quit the test App before reopening with the same command and HOME/state:
   APP="/path/to/test-copy/Lintel.app"
   env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin /usr/bin/open -g -n -a "$APP" \
     --env "HOME=$ROOT/home" --env "CFFIXED_USER_HOME=$ROOT/home" \
     --env "LINTEL_TEST_HOME=$ROOT/home" --env "LINTEL_STATE_DIR=$ROOT/state" \
     --env "LINTEL_BROWSER_STATE=$ROOT/browser-state" --env "TMPDIR=$ROOT"

A successful open only confirms that the launch request was sent; separately observe the actual window and selected environment. -g does not activate the App. Do not run multiple copies against the same test state. These variables isolate the specified HOME/state for this trial; they are not an OS sandbox and do not replace first-install acceptance on a clean Mac. The quickstart resolves ROOT to a physical path. Preserve that form for output paths as well; do not substitute a shorter path containing a symlink.

  1. Register from an empty workspace. Add an existing environment named Synthetic native trial, using the expanded absolute path of $ROOT/claude-root as its config directory. Register only; do not run Claude. Confirm that the selected host is this Mac and the environment is this fixture.
  2. Preview exact selection. Open Preserve work, choose Archive only and enable individual-file selection. Keep only CLAUDE.md, projects/example/memory/MEMORY.md and projects/example/session.jsonl, deselecting NOT_SELECTED.md. Use the absolute path of $ROOT/carried.age for output. Both capacity preflight and the approval plan must name exactly three files. No ciphertext should exist at preview time; settings and placeholder credentials must be excluded.
  3. Approve once and query the original task. Enter a passphrase used only for this synthetic trial and approve the current plan. Retain its original ID/hash. Wait for actual completion; acceptance is not completion. If uncertain, query the original ID without resubmission. The receipt must show archive-only with no new environment/root. Use the byte check in quickstart step 6 to verify all six originals, including the unselected file.
  4. Quit, reopen and read. Fully quit the App and relaunch with the same HOME/state. Check the original task in Records & recovery, then choose Standalone encrypted package in Sessions & data, entering the absolute ciphertext path and the passphrase again. The index must contain exactly the three selected files; instruction, memory and raw session text must be readable. Do not approve import, launch or cleanup. Separately verify reading in an independent HOME/state with quickstart step 7. Reopening the same state is not an independent installation.
  5. Record each result separately. Record observed startup, registration, exact selection, preview, approval, original-task completion, quit/reopen, file-based package reading and six-file byte checks. Missing automation windows, failed input or screenshot errors mean unverified; retain the error without labeling the product successful or broken. Keep raw screenshots, fixture, state, passphrase and internal records local; never upload the entire candidate evidence directory.

After the main path, separately observe Chinese/English menus, Day/Night/System and motion defaults. Open Help to verify the documentation revision and actual links, then check for an update once; an unconfigured feed must show that limitation rather than claim the App is up to date. In Terminal and Agent, choose the delivered CLI for this platform, check its candidate and HOME/UID/state, review and copy the handoff, and confirm that no new job appeared. Record removable-volume system authorization separately; see the CLI entry.

One record prepares three outputs

app-release.mjs is the local release-preparation entry. It creates no keys, signs nothing, uploads nothing, creates no GitHub Release and deploys no Pages site. Its input is a local lintel.app-release/1 record. Inputs containing actual artifact paths stay outside Git or in ignored directories; public outputs contain no local paths.

First choose the exact source revision, a strictly higher new version, channel, architecture and reviewed public update key. The following illustrates fields and is not real release data:

{
  "schema": "lintel.app-release/1",
  "version": "0.2.0-preview.1",
  "previous_version": "0.1.0",
  "channel": "preview",
  "source_revision": "<40-character-source-commit>",
  "pubkey": "<base64-encoded-public-key-file-content>",
  "notes": "Public changes and compatibility notes for this release",
  "pub_date": "2026-10-09T00:00:00Z",
  "platforms": {
    "darwin-aarch64": {
      "archive_path": "/path/to/Lintel.app.tar.gz",
      "signature_path": "/path/to/Lintel.app.tar.gz.sig",
      "dmg_path": "/path/to/Lintel.dmg",
      "archive_name": "Lintel_0.2.0-preview.1_aarch64.app.tar.gz",
      "dmg_name": "Lintel_0.2.0-preview.1_aarch64.dmg"
    }
  }
}

darwin-x86_64 is the separate Intel macOS target. The current inspector accepts single-architecture Mach-O; universal archives are outside this preparation path. Every public filename must contain the exact version; DMGs and updater archives are separate.

# Review build configuration first; the output directory must not exist.
node scripts/app-release.mjs configure \
  --record candidate-packages/app-release-input.json \
  --out candidate-packages/app-config

# Build from clean source with required static resources and toolchain prepared.
node scripts/app-release.mjs build \
  --record candidate-packages/app-release-input.json \
  --platform darwin-aarch64

# Verify actual built, signed files offline; outputs remain local candidates.
node scripts/app-release.mjs prepare \
  --record candidate-packages/app-release-input.json \
  --out candidate-packages/app-prepared

build checks that the current clean Git revision matches the declaration and that previous_version matches the current source App version. It fixes the Tauri target, app/dmg, createUpdaterArtifacts, public key and feed, and passes the same version to the frontend. Update-signing secrets use Tauri's supported local secret/environment mechanisms, never the input record, command line, source, frontend or public manifest. This command may invoke local signing tools and must run only under corresponding build/signing authorization.

prepare verifies the actual .app.tar.gz finite paths, entry types/capacity, Bundle ID, Info.plist version, Mach-O architecture of lintel-desktop, Minisign artifact/trusted-comment signatures and exact version, then computes SHA-256 for uploaded-byte comparison. It executes neither archive nor DMG. DMG byte checks do not prove installation works. source_revision is a declaration, not source authentication; Apple Developer ID/notarization remain unverified. Outputs include:

  • release.json: public candidate record, platforms, first-download information and byte evidence, without local paths.
  • updates/preview.json or updates/stable.json: a static Tauri feed candidate for that channel.
  • tauri-release.json from configure: a reviewable build override. Formal builds should use the build entry above to keep frontend/native versions aligned.

Update signatures protect the package and version accepted by the updater. Apple Developer ID code signing and notarization form a separate layer of macOS installation trust. Non-developer distribution must independently complete Apple notarization, without bypassing Gatekeeper.

Manual download shape (no updater feed)

A Preview without in-app updates uses a lintel.app-release-manual/1 record: same fields as the signed record, but without pubkey, archive_path, signature_path or archive_name; each platform declares only dmg_path and dmg_name. configure/build reject manual records (they pin the signed build configuration); prepare dispatches on the record schema and, for the manual shape, performs only the DMG frozen-identity and SHA-256 byte checks, emitting release.json (schema lintel.app-release-manual-public/1) and no updates/ feed. verify-public dispatches the same way and checks only the public DMG bytes.

prepare-site.mjs --app-manual <release.json> requires verified public bytes and projects the download buttons plus the "no in-app updates" note, but writes no updater feed; --app-release and --app-manual cannot be combined — one site payload carries one download story. The manual shape does not disable or loosen any existing signature check; once signing is in place, the updater is enabled through the original lintel.app-release/1 path.

node scripts/app-release.mjs prepare \
  --record candidate-packages/app-release-manual-input.json \
  --out candidate-packages/app-prepared-manual

Activation order when release is authorized

Each external release and hosting action still requires exact authorization. A signed updater release first completes signing/notarization and candidate-installation acceptance, then creates the matching GitHub Release and uploads each architecture's DMG, .app.tar.gz and .sig under the public names in the record. Keep version/tag/filenames immutable; never reuse a released version. An explicitly authorized unsigned developer Preview follows the manual-record/download path above, discloses unverified Apple trust and clean-Mac installation, and generates no updater feed.

After public artifact upload, verify the exact bytes first; activate the feed last:

node scripts/app-release.mjs verify-public \
  --record candidate-packages/app-prepared/release.json \
  --out candidate-packages/app-public-verified

node scripts/prepare-site.mjs \
  --media-dir candidate-packages/site-media \
  --app-release candidate-packages/app-public-verified/release.json \
  --out candidate-packages/site-with-app

verify-public reads only the HTTPS URLs for the fixed repository/tag in the record, compares actual byte counts and SHA-256, and writes another directory without changing old records. It requires large network downloads; reachability and identical bytes do not establish Apple signing, notarization or native use. prepare-site generates download links and feeds only from a record with verified public bytes. Binaries stay on GitHub, outside the Pages payload's 25 MiB file limit. Without a record, the site continues to show the source preview without a fake download.

If two channels are activated, pass both --app-release records to the same payload, retaining each original record so a whole-site update does not remove the other feed. First installation on the website prefers stable, otherwise preview. Version, download details and feed come from one record. updates/* and download metadata disable immutable caching. Follow site-hosting (Chinese) for preview/production/TLS/readback upload, then test checking, downloading, installing and original-task recovery from an older App on each channel. A source push activates none of this.

A feed failure leaves the current App in place. Signature/version mismatches refuse installation. For an incorrectly published candidate, stop new recommendations on that feed first, then publish a higher fixed version. Do not enable downgrades or replay old packages by changing their version number. Preserve earlier public files and original update records for manual recovery.

Browser extension/native host and remote runner installation are outside automatic App updates. A new App may carry new resources, but they still require their own frozen preview, explicit approval and original-installation reconciliation. Older remote tasks keep their frozen runner.

Protocol/API references: Tauri updater. Runtime behavior follows the pinned tauri-plugin-updater, the current CLI's signer sign --app-version, and repository checks. Source acceptance criteria are in the telemetry and updates Leaf (Chinese).

Unified candidate build and consistency gate (unreleased)

scripts/prepare-candidate.py requires Python 3.11+ (standard-library tomllib) and provides local build and verify modes. Commit and check the exact clean 40-character SHA first. The output directory must be absent and outside the source checkout. The matrix entry currently requires native macOS arm64, all three Rust targets, Node, cargo-zigbuild, Zig 0.16.0 and complete rust-docs notices for the active toolchain. Both Linux targets reuse the existing cargo zigbuild path; the Zig version must match the reviewed native-runtime notices. Preflight rejects missing prerequisites before creating output and installs no toolchains. Replace the sample paths and SHA with actual selected inputs:

python3 scripts/prepare-candidate.py build \
  --revision REPLACE_WITH_EXACT_CLEAN_40_HEX_SHA \
  --out ../lintel-candidate-build
# Add --app to that build command when preparing a macOS App/DMG.
python3 scripts/prepare-candidate.py verify \
  --receipt ../lintel-candidate-build/build-receipt.json \
  --ci-plan ../lintel-ci/plan.json \
  --ci-results ../lintel-ci/results.json \
  --ci-evidence ../lintel-ci/evidence \
  --out ../lintel-candidate-verified.json

build uses a fresh isolated source clone and fresh target, runs fixed locked builds for all three CLI platforms and their components, and records inputs and final archives. verify rereads actual tar member bytes instead of trusting package-declared checksums. It checks the complete platform matrix, components, versions, exact SHA and consistency with the canonical full CI plan/results/evidence, including clean checkouts. Relabeling a reduced plan as full is rejected. App-enabled builds also compare the App and resources in the actual DMG.

These remain local consistency observations: build receipts and CI JSON have no independently authenticated origin and are not trusted CI identity proofs. c7680f0 completed a real fresh-clone/fresh-target build of three CLI platforms (macOS arm64 and Linux x86_64/arm64 musl) and the macOS App/DMG. Downloaded dependencies were reused; this was not an empty-cache build. Current state records the complete candidate source SHA and matrix/full-CI status. Later proof-only documentation commits do not change the built candidate source revision. App installation, clean-Mac trust and Release acceptance remain unverified. The public App 0.1.1 and CLI 0.1.0 remain the previous release lines; current main is unreleased. Build, verification, native installation acceptance, signing/notarization, Release, downloads and feed activation remain separate steps, neither authorized nor performed automatically by this script.
